Programa de facturación en local

Facturín · un proyecto de Acenology

Haz facturas desde tu propio ordenador. Guardas tus clientes y tus productos una vez y, al crear una factura, el programa calcula solo el IVA, el total y el número de factura.

  • React + Vite
  • Node.js 24 + Express
  • SQLite
  • Funciona sin internet

01 · Qué hace

Facturas sin complicaciones

Pensado para un autónomo o un negocio pequeño que trabaja en un solo ordenador, sin internet y sin varios usuarios. Después de crear una factura puedes verla, imprimirla o guardarla en PDF.

  • Añadir y ver clientes (nombre, DNI, email y dirección).
  • Añadir y ver productos con su precio y su IVA (0, 4, 10 o 21 %).
  • Crear una factura: elegir cliente, fecha y productos con su cantidad.
  • Ver el listado de facturas, ordenado por fecha.
  • Ver una factura completa, con el desglose del IVA, e imprimirla o guardarla en PDF.
  • Ver el total en dólares, libras y francos suizos.
Idea clave

El dinero va en céntimos

Todos los importes se guardan como números enteros de céntimos: 12,50 € se guarda como 1250. Así se evitan los pequeños errores de los ordenadores con decimales (0.1 + 0.2 no da exactamente 0.3) y las cuentas siempre cuadran.

Idea clave

El backend hace las cuentas

El frontend solo envía cliente, fecha, productos y cantidades. El backend saca el precio y el IVA de la base de datos, calcula los totales y pone el número de factura (2026-0001, 2026-0002…). Todo se guarda en una transacción: o se guarda entero, o nada.

Lo que queda para más adelante (editar y borrar, facturas rectificativas, descuentos, cantidades con decimales, usuarios…) está en docs/esquema.md.

02 · Instalación

Cómo instalarlo y arrancarlo

Lo que necesitas

  • Node.js 24 (incluye npm), de nodejs.org. Hace falta esta versión porque el módulo node:sqlite solo existe en las versiones recientes.
  • Git, para descargar el proyecto.

Para comprobar tu versión de Node, escribe en una terminal node --version. Debe salir algo que empiece por v24.

Instalación

  1. Descarga el proyecto: 
    git clone https://github.com/ALEXMORENTO/facturacion.git
cd facturacion
  2. Instala las dependencias (las de la raíz, el backend y el frontend) con un solo comando: 
    npm run instalar

Si usas Facturin.bat no hace falta este paso: la primera vez instala solo lo que falte.

Arrancarlo

El programa son dos partes que funcionan a la vez: el backend (el servidor) y el frontend (las pantallas). Hay dos formas fáciles de encender las dos de golpe:

Forma 1 · Windows

Doble clic

Haz doble clic en Facturin.bat. Se abre una ventana negra que comprueba que tienes Node, instala lo que falte la primera vez y abre el navegador en http://localhost:5173.

Para pararlo: cierra esa ventana.

Forma 2 · Terminal

Un comando

Desde la carpeta raíz del proyecto:

npm run dev

Verás los mensajes de las dos partes, con su etiqueta: [backend] en azul y [frontend] en verde. Para pararlo: Ctrl + C.

Forma manual · Dos terminalesOpcional, si prefieres ver cada parte por separado.

Terminal 1 — backend

cd backend
npm run dev

Verás Servidor escuchando en http://localhost:3001. La primera vez se crea solo el archivo backend/facturacion.db con las tablas vacías.

Terminal 2 — frontend

cd frontend
npm run dev

Abre la dirección que aparece (normalmente http://localhost:5173).

¿Cómo se hablan las dos partes? El frontend pide los datos a rutas que empiezan por /api, y Vite las reenvía al backend en el puerto 3001 (configurado en frontend/vite.config.js). Si el backend está apagado, verás el aviso “No se ha podido conectar con el servidor”.

03 · Tecnologías

Qué usamos y por qué

Cada tecnología responde a cuatro preguntas: qué es, para qué la usamos, por qué la elegimos y qué alternativa descartamos. Pulsa en cada una para abrirla.

PiezaTecnologíaEn una frase
PantallasReact + Vite + React RouterLa forma más usada de hacer pantallas web, rápida al programar.
ServidorNode.js 24 + ExpressEl mismo lenguaje (JavaScript) en todo el proyecto.
Base de datosSQLite con node:sqliteTodo en un archivo, sin instalar nada aparte.
React frontendConstruir pantallas a base de piezas, como LEGO.

Qué es

Una librería de JavaScript para construir pantallas web a base de piezas (componentes). Haces una pieza “menú lateral”, otra “tabla de facturas”… y las encajas. Si cambias una pieza, cambia en todos los sitios donde se usa.

Para qué la usamos

Para todas las pantallas: Inicio, Clientes, Productos, Facturas y Ver factura (frontend/src/pages/), y las piezas reutilizables (frontend/src/components/).

Por qué

  • Es la herramienta más usada: muchísima documentación y respuestas a casi cualquier duda.
  • Cuando los datos cambian, actualiza la pantalla sola.
  • Lo aprendido sirve para muchos otros proyectos.

Descartado

  • HTML y JavaScript “a pelo”: con seis pantallas y formularios, el código se vuelve un lío.
  • Vue o Angular: buenas opciones, pero React tiene más comunidad y ejemplos.
Vite frontendEl “horno” rápido que prepara las pantallas y hace de intermediario con /api.

Qué es

Una herramienta que prepara y sirve el frontend mientras programas. Tú escribes la receta (el código React) y Vite la “cocina” para el navegador. Al guardar un cambio, la página se actualiza sola.

Para qué la usamos

  • Arranca el frontend en http://localhost:5173.
  • Hace de proxy: lo que empieza por /api se lo pasa al backend (puerto 3001).

Por qué

  • Arranca en un momento y recarga casi al instante.
  • Es la forma recomendada hoy para empezar con React.
  • El proxy evita escribir el puerto del backend en el código.

Descartado

  • Create React App: mucho más lento y ya no se mantiene.
  • Next.js: muy potente, pero mezcla frontend y backend y añade conceptos que no necesitamos.
React Router frontendEl recepcionista que te manda a la pantalla correcta según la dirección.

Qué es

Una librería que decide qué pantalla se ve según la dirección (URL) del navegador.

Para qué la usamos

En frontend/src/App.jsx están las rutas: /, /clientes, /productos, /facturas, /facturas/:id y una página de “no encontrada”. El menú lateral se queda fijo y solo cambia la parte central.

Por qué

  • Es la librería de rutas más usada con React.
  • Funcionan los botones “atrás” y “adelante” y puedes guardar en favoritos una factura.
  • Cambiar de pantalla es instantáneo.

Descartado

  • Un if con una variable “pantalla actual”: perderíamos las direcciones propias, el botón “atrás” y los favoritos.
Node.js 24 backendJavaScript fuera del navegador, con base de datos incluida.

Qué es

Un programa que ejecuta JavaScript directamente en tu ordenador. Es como sacar al cocinero del restaurante (el navegador) y dejarle cocinar en casa: mismo idioma, pero ahora puede leer y guardar archivos.

Para qué la usamos

Para ejecutar el backend, instalar dependencias con npm y hacer funcionar Vite.

Por qué (y por qué la versión 24)

  • Es JavaScript, como el frontend: un solo lenguaje para todo.
  • La versión 24 trae node:sqlite para usar la base de datos sin instalar nada más.
  • Con node --watch el backend se reinicia solo al guardar.

Descartado

  • Python (Flask, Django) o PHP: habría que aprender un segundo lenguaje.
  • Node 18 o 20: no traen node:sqlite de serie.
Express backendEl camarero que recibe los pedidos, comprueba y responde.

Qué es

Una librería para Node que crea un servidor web: recibe peticiones (“dame la lista de facturas”) y devuelve respuestas.

Para qué la usamos

El backend escucha en http://localhost:3001 con estas rutas:

RutaQué hace
/api/clientesVer y añadir clientes
/api/productosVer y añadir productos
/api/facturasVer y crear facturas (IVA, totales y número)
/api/divisasPasar el total a dólares, libras y francos suizos
/api/saludResponde “estoy encendido”

Por qué

  • Es la librería de servidor más conocida de Node.
  • Con pocas líneas tienes una ruta funcionando.
  • No impone una organización rígida, ideal para un proyecto pequeño.

Descartado

  • node:http sin librería: habría que escribir a mano lo que Express ya resuelve.
  • Fastify o NestJS: menos ejemplos para principiantes, o demasiado complejo para este tamaño.
SQLite con node:sqlite base de datosUn archivador entero que cabe en un solo archivo.

Qué es

Una base de datos que guarda todo en un único archivo, con cajones (tablas) para clientes, productos, facturas y líneas de factura.

Para qué la usamos

El archivo es backend/facturacion.db y se crea solo la primera vez (backend/src/db.js). Activamos las claves foráneas (no se puede facturar a un cliente que no existe) y las facturas se guardan con transacciones.

Por qué

  • No hay que instalar ni configurar ningún programa aparte.
  • Copia de seguridad = copiar facturacion.db.
  • Perfecta para una persona en un ordenador.

Descartado

  • PostgreSQL o MySQL: programas aparte que instalar y configurar; tienen sentido con muchos usuarios por internet.
  • better-sqlite3: una dependencia más, que a veces falla al instalarse en Windows.
  • Archivos JSON: sin transacciones ni claves foráneas.
Git + GitHub trabajoHistorial de cambios, ramas como borradores y Pull Requests para revisarlos.

Por qué

  • Si algo se rompe, puedes volver a una versión que funcionaba.
  • Cada tarea va separada: si una sale mal, no estropea las demás.
  • El PR obliga a mirar los cambios antes de juntarlos.
  • GitHub sirve además de copia de seguridad.

Descartado

  • Copiar carpetas (facturacion-v2, facturacion-final…): es fácil perderse.
  • Una sola rama main: cualquier cambio a medias quedaría en la versión “buena”.

Cómo se usa en el día a día: ver Flujo de Git.

Las explicaciones completas están en docs/decisiones-tecnicas.md.

04 · Arquitectura

Cómo se conectan las piezas

Cada pieza solo habla con la de al lado. El frontend nunca toca la base de datos ni internet: todo pasa por el backend.

Navegador

Lo que ves: Chrome, Edge, Firefox…

abres localhost:5173
Frontend
puerto 5173 · React + Vite

Muestra datos y recoge lo que escribes. Pasa céntimos a euros para enseñarlos.

peticiones a /api/… (proxy de Vite)
Backend
puerto 3001 · Node.js 24 + Express

Comprueba los datos, calcula IVA, totales y número de factura, y guarda. Todo en céntimos.

lee y escribe
Base de datos
SQLite · facturacion.db

Clientes, productos, facturas y líneas.

pregunta el cambio del día
API Frankfurter
externa · necesita internet

Tipos de cambio del Banco Central Europeo (USD, GBP, CHF).

Las tres reglas que hay que recordar

  1. El frontend nunca toca la base de datos ni la API externa. Solo habla con el backend a través de /api.
  2. El backend es el único que calcula y el único que guarda. Así todas las comprobaciones están en un solo sitio.
  3. El dinero viaja siempre en céntimos enteros. Solo se convierte a euros al final, para mostrarlo.

05 · Divisas

El total en otras monedas

En la pantalla Ver factura, debajo del total, aparece cuánto sería en dólares (USD), libras (GBP) y francos suizos (CHF), con la fecha del cambio.

Total125,00 €
USD$ …
GBP£ …
CHFCHF …

Ejemplo ilustrativo: las cifras reales dependen del cambio del día.

Los datos vienen de Frankfurter, un servicio gratuito que publica los tipos de cambio oficiales del Banco Central Europeo cada día laborable. Una API es una “ventanilla” a la que un programa le hace preguntas: es como llamar al banco y preguntar “¿a cuánto está el dólar hoy?”.

El camino de una petición

  1. El frontend pide a nuestro backend: /api/divisas?centimos=12500
  2. El backend (backend/src/routes/divisas.js) pregunta a Frankfurter el cambio del día.
  3. Hace la conversión y la redondea al céntimo, para seguir con números enteros.
  4. Devuelve el resultado al frontend, que lo muestra en euros, dólares, libras y francos.

¿Y si no hay internet? Si Frankfurter no responde o tarda más de 5 segundos, el backend contesta con un mensaje en español y el resto de la factura se sigue viendo con normalidad. Es la única parte de Facturín que necesita internet.

Por qué Frankfurter

Coste

Gratis y sin clave

No hay que registrarse ni guardar contraseñas de acceso.

Fuente

Datos oficiales

Los publica el Banco Central Europeo.

Arquitectura

Desde el backend

Nunca desde el navegador: así se respeta la regla de que el frontend solo habla con /api.

Descartado: APIs de pago o con clave (innecesario), escribir los cambios a mano (serían falsos al día siguiente) y llamar a Frankfurter desde el frontend (rompería las reglas).

06 · Mejoras

Validaciones y arranque fácil

Validaciones de DNI, email y fechas

El backend revisa los datos antes de guardarlos. Si algo está mal, no guarda nada y devuelve un mensaje claro en español, que la pantalla muestra en rojo. Las comprobaciones están en backend/src/utils/validaciones.js.

DatoQué se comprueba
DNI / NIE / CIF Que tenga el formato correcto y que la letra o el dígito de control cuadre con el número, igual que hace Hacienda. Antes se limpia: 12.345.678-z se guarda como 12345678Z.
Email Que tenga la forma nombre@empresa.com, sin espacios.
Fecha de factura Que sea un día real (AAAA-MM-DD) y que no sea anterior a la última factura, porque la ley obliga a que numeración y fechas vayan en orden.
Productos y líneas Precio en céntimos ≥ 0, IVA de 0, 4, 10 o 21 %, cantidades enteras mayores que 0 y productos que existan.

DNI y email siguen siendo opcionales, pero si se escriben tienen que ser válidos.

Arranque fácil

Antes había que abrir dos terminales y escribir un comando en cada una. Ahora basta un doble clic.

La llave

concurrently

Una herramienta que ejecuta varios comandos a la vez. Arranca los dos motores (backend y frontend) de golpe con npm run dev. Funciona igual en Windows, Mac y Linux.

El botón de arranque

Facturin.bat

Comprueba que hay Node, instala lo que falte la primera vez y lanza npm run dev. Cualquiera puede usar Facturín sin abrir una terminal.

Descartado: el símbolo & para lanzar dos comandos (funciona distinto en Windows y no siempre para los dos con Ctrl + C) y Docker (demasiado para un programa local).

07 · Forma de trabajar

Flujo de Git

Git guarda el historial de cambios; las ramas son borradores donde trabajar sin estropear nada, y un Pull Request (PR) es la petición para pasar ese borrador a limpio, revisándolo antes.

mainProducción: la versión buena y terminada.
developDesarrollo: donde se juntan las tareas acabadas.
feature/...Una funcionalidad nueva. Ej.: feature/divisa.
chore/...Mantenimiento que no cambia lo que hace el programa. Ej.: chore/arranque-facil.
docs/...Cambios solo en la documentación. Ej.: docs/decisiones-tecnicas.

Los pasos de cada tarea

  1. Partir de develop actualizado y crear una rama nueva: 
    git switch develop
git pull
git switch -c feature/nombre-de-la-tarea
  2. Hacer los cambios y guardarlos con commits pequeños, con formato conventional commits: feat: (algo nuevo), fix: (arreglo), docs: (documentación), chore: (mantenimiento).
  3. Subir la rama a GitHub: 
    git push -u origin feature/nombre-de-la-tarea
  4. Abrir un Pull Request hacia develop, revisarlo y fusionarlo.
  5. Cuando develop está estable, otro Pull Request la pasa a main.

Nunca se trabaja directamente sobre main ni sobre develop: todo entra a través de un Pull Request.
